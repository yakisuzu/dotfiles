# GitHub Retrospective

指定期間の自分の GitHub 実績を集計し、振り返り用の markdown レポートを生成する。
PR として出した進捗が主役。issue は集計しない。

**報告用ドキュメントなので、テーマ要約はコード識別子 (クラス名・関数名・API 名等の英単語)
ではなく機能名・日本語で書く**。「OptionalId から ProviderId 除去」ではなく
「契約や顧客の内部 ID モデルの整理」のように、コードを読まない人にも伝わる表現にする。
PR タイトルの羅列部分はそのままでよい。

## Workflow

### 1. 期間とスコープを確定する

- **期間**: ユーザーの指定 (「先月」「4〜6月」「2026-06」等) を `YYYY-MM-DD..YYYY-MM-DD` に自分で解決する。`date` コマンドに頼らず、今日の日付から計算してよい。
- **スコープ**: ユーザー指定の org / repo を `gh search` の引数に変換する。
  - org 指定 → `--owner <org>` (例: `--owner my-org`)
  - repo 指定 → `--repo <owner>/<repo>`
  - 指定がなければユーザーに確認する (全 org 横断は意図しないノイズが混ざりやすい)。

### 2. 実績を取得する

同梱スクリプトを実行する:

```bash
bash ~/.claude/skills/github-retrospective/scripts/fetch_activity.sh \
  YYYY-MM-DD YYYY-MM-DD --owner <org> > /tmp/gh-retro.json
jq '{merged: (.merged_prs | length), open: (.open_prs | length)}' /tmp/gh-retro.json
```

- `merged_prs`: 期間内にマージされた自分の PR (メイン)
- `open_prs`: 期間内に作成され未マージの PR (進行中として報告)

**件数が limit (merged: 300 / open: 100) に達していたら取りこぼしがある**。その場合は期間を分割して再実行し、レポートに全件反映する。取りこぼしたまま黙って集計しない。

### 3. レポートを書く

出力先: ユーザー指定があればそこ、なければ `~/.claude/retrospectives/retro-<START>_<END>.md`
(ディレクトリがなければ作成する)。

構成:

```markdown
# GitHub 振り返り (START 〜 END)

## サマリ
- マージ済み PR: N 件
  - owner/repo: n 件（件数降順で全 repo を列挙）
- 進行中 (期間内作成・未マージ): K 件

## 1. 主な成果
主要テーマを **3 つ** (ユーザー指定があればその数) に絞り、各テーマの成果を
機能名ベースの日本語 2〜4 行で要約する。件数の羅列ではなく
「何をしたか／どんな価値を出したか」が読み取れる文章にする。

### テーマ (機能名の見出し)

### 補足
テーマに入らなかった活動をテーマ単位の箇条書きで列挙する。
説明の段落にはせず、1 行 = 1 テーマ (機能名の見出し + 短い要約) で書く。
(例: 不具合修正・運用対応、テスト基盤、依存整理など)

### 意識・工夫したこと、新しい試み
成果物ではなく「働き方・仕組みへの投資」を書く小節。冒頭に
`テーマ: **...**` として期間を貫く方針を 1 行置き、続けて試みを箇条書きにする。
初稿は PR から読める試み (skill 整備、自動化、段階的リリース、テスト並行整備など)
を置き、対話で本人の意図・認識を補って仕上げる。

## 2. 課題・うまくいかなかった点
初稿は PR データから観測できる兆候をもとに **下書き (仮説)** として書く:
revert された取り組み、障害対応・復旧系 PR、長期化・反復した修正
(flaky 対策や同種の fix の繰り返し) など。
各項目に根拠となる PR・出来事を添え、「(仮説)」であることを明記する。

## 3. 次の期間で伸ばしたいこと
初稿は 1・2 から素直に導ける候補 (継続中のテーマの完遂、課題の裏返し) を
箇条書きで置くに留める。本命はユーザーとの対話で埋める。

## リポジトリ別 PR 一覧
### owner/repo (n 件)
- PR タイトル ([#123](url))
（マージ日昇順。進行中 PR は末尾に「🚧 進行中」を付けて同じ節に含める）
```

セクション 2・3 は目標や体感に関わるため PR データだけでは書き切れない。
**初稿を出力した後、ユーザーと対話してブラッシュアップする** (次の Step 4)。

### 4. 報告と対話ブラッシュアップ

書き終えたら以下を簡潔に伝える (全文の貼り付けはしない):

- 出力ファイルパス
- サマリ数値 (マージ PR 数 / リポジトリ別内訳 / 進行中数)
- 主な成果のテーマ見出しだけ

続けて **セクション 2・3 のブラッシュアップ用の質問** を投げる:

- セクション 2: データから拾った仮説を提示し、「実際に課題と感じた点・データに
  現れない課題 (使われなかった機能、目標とのギャップ等) はあるか」を聞く。
  他メンバーの障害のカバー対応など、本人の課題でないものは対話で除外する
- セクション 3: 期初・上位の目標があれば教えてもらい、1・2 と繋げて書き直す。
  「達成できているか」「浸透しているか」という体感には、可能なら裏付けデータを
  添える (例: 月別 PR 件数の推移、共有リポジトリへの他メンバーの貢献数を
  `gh pr list` / `gh api repos/.../commits?path=...` で集計)

回答を受けてセクション 2・3 (必要なら 1 も) を更新する。1 往復で完成させようと
せず、ユーザーが満足するまで対話を続ける。

## Notes

- `gh` が対象 org に認証済みであること。
- `gh search` API は検索インデックス由来のため、直近数分の活動は反映されないことがある。
- レビュー実績 (`reviewed-by:@me`) は現状スコープ外。必要になったら
  `gh search prs --reviewed-by=@me --merged-at ...` を同じ要領で足す。
